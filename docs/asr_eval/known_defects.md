### 一、现象

`language` 取默认值 `auto` 时，中文音频的识别输出是**繁体**：

| `--language` | 识别输出（前 40 字） |
|---|---|
| `auto` | `'同學們好,今天這節刻,我們來講戰機神經網絡,以及它背後最重要的訓練算法,反向傳播'` |
| `zh` | `'同学们好,今天这节课,我们来讲《卷机神经》网络,以及它背后最重要的训练算法,反向'` |

同一份音频、同一份参考文本，只因这个参数不同，CER 从 **0.1636** 变成 **0.5198**。

### 二、证据链

**① 判定条件**（`backend/asr/whisper_engine.py`）：

```python
SIMP_HINT = "以下是普通话的句子，请使用简体中文转写。"      # :195
SIMP_HINT_LANGS = frozenset({"zh", "zh-cn", "zh-tw"})        # :197  ← 不含 "auto"
```

注入点两处，都按同一个集合判断：

```python
self._echo = EchoCleaner(                                     # :267-269
    get_simp_hint() if (self.language or "").lower() in SIMP_HINT_LANGS else ""
)
hint = (                                                      # :922-926
    get_simp_hint() if (self.language or "").lower() in SIMP_HINT_LANGS else ""
)
```

⇒ `self.language == "auto"`（字符串，见 `:249` 赋值；`:604` 才把它折成 `None` 传给 Whisper）
时，`"auto" not in SIMP_HINT_LANGS` ⇒ **引导语根本不注入**。

**② 默认值四处都是 `auto`**：

| 位置 | 代码 |
|---|---|
| 前端新建课程表单 | `frontend/src/pages/CourseList.tsx:25` / `:42`（`language: 'auto'`） |
| 前端课程配置页 | `frontend/src/pages/CourseConfig.tsx:210` / `:224`（`course?.language \|\| 'auto'`） |
| 后端请求模型 | `backend/api/routes.py:68` / `:132`（`language: str = "auto"`） |
| 后端管道取配置 | `backend/asr/pipeline.py:64` / `:94` / `:149`（`course_config.get("language", "auto")`） |

⇒ 用户**不主动动那个下拉框**，走的就是 `auto`。

**③ 单变量对照**（同一素材 `synth_clean_short_zhlecture_cnn.wav`，`--terms on` 固定）：

| `--language` | `--term-language` | `termPromptSections.phrases` | `termPromptMd5` | `accuracy.cer` | 输出 |
|---|---|---|---|---|---|
| `auto` | `auto` | 60 | `0f5e8159…` | **0.5198** | 繁体 |
| `auto` | `zh` | 0 | `d41d8cd9…`（空串） | **0.4617** | 繁体 |
| `zh` | `auto` | 60 | `0f5e8159…` | **0.1900** | 简体 |
| `zh` | `zh` | 0 | `d41d8cd9…`（空串） | **0.1636** | 简体 |

**读数**：第 1 行与第 3 行的提示词 md5 **完全相同**（`0f5e8159…`），简繁却翻转
⇒ **`--language` 是主因，与短语层无关**。`--term-language` 只贡献次要伤害
（同样 `auto` 下 0.5198 → 0.4617；同样 `zh` 下 0.19 → 0.1636，量级 +0.03~0.06）。

**④ 与设计意图矛盾**（这是判断「遗漏 vs 取舍」的关键）：

`whisper_engine.py:194` 的注释写着：

> 但术语表可能为空（新课程、用户没选领域），所以**必须显式注入**这句，不能靠术语表顺带解决。

即设计意图是「任何情况下都要让简体中文出现在提示词里」。而 `auto` 恰恰是**最容易术语表为空**
的那条路径（新课程默认值），却没有注入 ⇒ **更像遗漏，不像有意取舍**。

### 四、影响面

- **谁**：用中文课程、且没手动改过「语言」下拉框的用户 —— 即默认路径上的绝大多数中文用户。
- **多严重**：字幕仍是**可读**的（繁体 ≠ 乱码），但：① 与用户输入的简体术语/笔记不一致；
  ② 逐字稿导出、术语高亮、生词本匹配都会因字形不同而**失配**；
  ③ 评估口径上，CER 会被字形差异吃掉 **+0.35 以上**，让「识别质量」看起来比实际差一倍。
- **不会影响**：英文 / 日文 / 韩文课程（`SIMP_HINT_LANGS` 本就该排除它们）。

### 五、修法候选与**最终采纳路线**

立项时列了 4 条候选，**最终采纳的是第 5 条（下面 e）** —— 前 4 条共同的死结是
「引导语必须在**解码之前**进 prompt，而语种要**解码之后**才能从 `info.language` 读到」，
所以只能在二者之间做取舍。e 用一次**前置的 encoder-only `detect_language()`** 把这个死结解开。

| # | 修法 | 代价 | 风险 | 采纳 |
|---|---|---|---|---|
| a | `auto` 时也注入引导语（把 `"auto"` 加进 `SIMP_HINT_LANGS`） | 一行 | **高** —— 英文课会被塞进一句中文，可能把输出带偏。**必须先用英文素材做对照**才能定 | ❌ 弃 |
| b | 首段识别后拿 `info.language`，检测到 `zh*` 就把 `self.language` 改成 `zh`（并同步 `_echo`） | 中（需改引擎状态机） | 低，但**第一段**仍是繁体 | ❌ 弃（残留第一段繁体） |
| c | 前端新建课程默认值改 `zh` | 一行 | 低，但英文课用户变成需要手动改（把问题换了个方向） | ❌ 弃 |
| d | 保持现状，仅本文档登记 | 零 | 用户侧无感知改善 | ❌ 弃 |
| **e** | **解码前探测**：`auto` 下先跑一次 `detect_language()`，用**同一次决策**同时定 `decode_lang` 与「要不要注引导语」；置信不足则降级为不强制（V5-2）；判定后**按会话粘滞**（V5-3 替换案）避免逐块翻转 | 每次会话最多付几次探测开销 | 低 —— 决策与注入同源，且给了降级与粘滞两条退路 | ✅ **采纳（V5-1/V5-2/V5-4）** |

**共同代价**：a/b/c 都要动 `backend/` 或 `frontend/` 生产代码 ⇒ **必须重新打包**
⇒ 现有 L4（`packaging/verify/report-v341.json`）与真机 e2e 结论**全部作废**，需重跑。
（划界见 [`write-boundary.md`](./write-boundary.md)：`frontend/{electron,package.json,node_modules,dist}`
与 `backend/`（非 tests）改动都会改 `setup.exe` 的哈希。）

**实际发生的事**：e 路线确实动了 `backend/` 生产代码 ⇒ 已按上面这条纪律走了完整的
**重新打包 + L4 + 真机 e2e** 流程，`v3.4.1` 交付物归档到 `_frozen_v341/`（md5 未变），
新交付物为 **`v3.5.0`**（指纹见 §16.5）。

### 七、产品侧度量（V6 批 A，2026-10-12）

关闭时留的第 3 条缺口（繁体对术语高亮 / 生词本的影响）在 V6 批 A 落地为一次**可复现的
基线测量**：`backend/tests/test_d1_traditional_terms.py`（6 条，**不改任何生产代码**）。

先明确「为什么繁体不是已经没了」——简体引导语只保证**识别输出默认是简体**，繁体仍从两条
路径进来：① 用户把课程配置的「中文输出字形」切成**保留原始字形**（`simpMode=raw`，
面向古文 / 繁体教材课程）；② 用户在**自定义术语**里填繁体词（界面上没有任何简繁校验）。
且实测显示繁体常是**字级混入**（`图表繪制`、`橫坐标`），不是整词繁体 —— 两种形态都进了样本。

| 指标 | 定义 | 实测（本机，2026-10-12） |
|---|---|---|
| **M1a 命中率**（有简繁差异的样本） | 库里存简体时，繁体形态在 `GET /vocabulary/{word}` 返回 200 的比例 | **0 / 22 = 0.0000** |
| **M1b 命中率**（简繁同形样本，**对照组**） | 同上，但样本本身无简繁差异 | **2 / 2 = 1.0000** |
| **M2 入库率** | 繁体形态经 `POST /vocabulary/{word}/collect` 成功入库的比例 | **24 / 24 = 1.0000** |
| **M3 重复条目** | 同一术语的简体与繁体形态并存产生的额外条目 | 生词本 **46** 条 vs 术语 **24** 个 → 额外 **22** 条（0.9167） |
| **M4 失败归因** | 未命中是「词表存的是简体」还是「匹配算法不认简繁」 | **责任方是数据形态**（见下） |

**样本**：24 个原生术语（从 `scripts/ab_terms_compare.py` 的 `COURSE_TERMS_ORIGIN`
**importlib 动态加载**，不复制副本；清单与映射表双向对拍，漏一个词即红）
+ 2 条真实观测到的字级混入形态（`图表繪制` / `橫坐标`，取自
`testset/chinese_lecture/real/*.corrections.tsv`）。其中 2 个词（`厘米` / `毫米`）
**简繁同形**，单独作为对照组 —— 首版把它们和实验组混算，得到「总命中率 2/24 = 8.3%」，
看起来像「有 8% 能命中」，把整件事盖住了。

**M4 归因怎么做的**：同一份代码、同一个查询，**只换**库里那条记录的字 ——

| 库里存 | 查简体 | 查繁体 |
|---|---|---|
| 简体 `坐标系` | 200 ✅ | **404** |
| 繁体 `坐標系` | **404** | 200 ✅ |

两边**完全对称** ⇒ 查词算法既不认简体也不认繁体，它只做**逐字相等比较**。
所以未命中的责任方是**库里那个字符串的形态**，不是「匹配算法不支持简繁」。
（踩坑：首版把两个方向写在**同一门课程**里，两条记录并存 ⇒ 两边都命中 ⇒
把「对称性」这个唯一结论糊掉；现改为两门各自新开的课程。）

**三条结论**：

1. **繁体形态从不命中**（22/22）—— 不是算法坏，是词表存简体，逐字比较必然不等；
2. **简繁同形的词全部命中**（2/2 对照组）⇒ 证明「不命中」确实由字形差异造成，
   而非查词链路整体失灵（对照组失效则 M1 结论不成立，故它是断言而非装饰）；
3. **入库不受影响**（24/24），但**产生重复条目**（同一术语简繁两形态各占一条，24 → 46）。

⚠️ `test_conclusion_premise_change_must_surface` 是**文档同步报警器**：若将来补上简繁
归一化，这几条会红，红的含义是「请更新本文档 D1 与 `plan_v6.md` §2.5」，
**而不是删断言让它变绿**。

## D2 · 延迟指标在 6/7 格上「不可得」——VAD 块 ↔ whisper 段的 1:N 结构性配对缺陷

| 项 | 值 |
|---|---|
| 状态 | ✅ **已关闭**（#175，2026-10-10 立项 / 2026-10-11 验证；口径为**新增**，旧口径保留作对照）；**V6-6（2026-10-15）补齐 1:N 的恒等式覆盖**（§五） |
| 严重度 | 中 —— 不产出错误数字，但让一个**度量方法学缺陷**伪装成「这批数据没有延迟」 |
| 发现于 | P2 #173 逐格基线（§14.6 已如实记账） |
| 影响文件 | `scripts/eval_asr_quality.py`（**不进安装包**，见 `write-boundary.md`） |

### 一、现象

`--realtime` 下延迟指标只在 `lowvol` 一格算得出，其余 6 格 `latency.p95` 落 `0.0` 占位：

| 场景 | 片段（VAD 块） | 字幕（whisper 段） | `paired` |
|---|---|---|---|
| clean / noise / fast | 6 | 10 / 9 / 8 | `False` |
| lowvol | 6 | 6 | **`True`** |
| multi | 6 | 10 | `False` |
| long | 56 | 82 | `False` |
| real | 63 | 86 | `False` |

### 二、根因：两个集合是 1:N，不是 1:1

- `Recorder.segments` 记的是 **VAD 语音块**（绑在 `VoiceActivityDetector(on_speech_segment=…)`）；
- `Recorder.subtitles` 记的是 **whisper 段**（`WhisperEngine.on_partial` 回调）。

一个 VAD 块里可以含好几个 whisper 段 ⇒ **字幕恒多于片段**（实测 6→10 / 56→82 / 63→86）。
旧实现要求 `len(segments) == len(subtitles)` 才配对 ⇒ **在原理上永远不可靠**，
`lowvol` 的 6→6 只是巧合。

⚠️ 旧注释把原因写成「一旦发生**合并降级**（多个片段并成一次识别），条数就不相等了」——
那是「字幕变**少**」的罕见方向，**把常态的结构性原因掩盖成了一个边缘机制**。

### 三、修法（已实施，纯新增）

`on_partial(text, words)` 本来就随文本交了词级时间戳（`WordTimestamp{word, start, end, confidence}`），
旧代码在 `Recorder.on_subtitle` 里把 `words` 丢掉了。新增**不依赖配对**的口径：

```
latency_word_based = pushWall − (feed_t0 + audioWordsEnd)
```

- 锚点从「所属 VAD 块结束」换成「**这条字幕自己最后一个词的结束**」⇒ 不需要配对，7 格全部算得出；
- 旧字段 `latency` 与 `pair()` **一字未动**，仍按 1:1 输出，供对照；
- 无数据时给 `None`，**不用 `0.0` 占位**（0.0 会把「算不出来」读成「延迟极小」）。

**定义性恒等式**（两套口径唯一的差别）：

```
latency_新 − latency_旧 == seg.audioEnd − audioWordsEnd >= 0
```

VAD 块尾通常挂着静音 ⇒ 新口径恒 ≥ 旧口径，差值恰是静音尾巴长度。
实测 `lowvol` **6/6 条残差 0.0000**，六条尾巴 `1.276 / 0.564 / 1.516 / 0.760 / 0.356 / 0.932`。
恒等式可**从报告独立重算**（`segmentDetail` ⊕ `latency_word_based.detail`，都已落盘）。

### 四、验证

| 项 | 结果 |
|---|---|
| 单元测试 | `backend/tests/test_eval_latency_words.py` **17 条**（含恒等式、方向性、反向断言、接线守卫） |
| 变异探针 | `packaging/verify/probe_latency_words_mutations.py` **13/13** 变异全被抓住 |
| 回归基线 | `npm test 157/0`、`tsc 0 错`、`pytest 391 通过 / 1 跳过` |
| 交付物指纹 | **未变** —— 改动全在 `scripts/`，不进安装包 |
| 旧口径 | 保留原样，历史报告仍可逐格对账 |

### 五、残留缺口（关闭时 / **V6-6 后**的对照）

| 缺口 | 关闭时（2026-10-11） | V6-6 后（2026-10-15） |
|---|---|---|
| **`long` / `real` 的恒等式不可校验**（1:N，旧口径没有明细可比） | ❌ 残缺 —— 恒等式只覆盖 `lowvol` 一格（`multi` 亦为 6→6，可配） | ✅ **已补** —— 新增「whisper 段 → VAD 块」**时间包含映射**（`Recorder.words_latency_by_block()`），1:N 下恒等式逐条可校验；规则四条见 `plan_v6.md` §3.2 |
| 新口径**逐字幕**，不区分「首段 / 续段」，按块聚合需另加映射 | ❌ 残缺 | ✅ **已补** —— 同一映射即按块聚合：`segIndex` 把每条字幕归到它的块，`mapped/unmapped/overlapped` 三个计数一起落盘 |
| `latency_word_based` 全部是**墙钟量**，跨会话不可比 | ❌ 仍缺（属测量学，非代码） | ✅ **口径已定案** —— V6-5 把七格各重复 N 次（31 次观测），**确认逐会话单调漂移 ≈ +0.2 s/会话** ⇒ 正式钉死「**跨会话不设阈值，时序量只走同会话对照**」，区间表见 `WER_REPORT_PLAN.md` §7.6。⚠️ 这是**测量学的固有限制**（不可"修"），只可"记录 + 纪律" |

**V6-6 的映射规则（先定义才可测）**：① 词尾落在哪个块的闭区间内就归那个块；
② 块尾静音归块内**最后一条**字幕（这是结论而非规定：块内每条的 `新−旧` 都等于
`seg.audioEnd − 该条自己的 audioWordsEnd`）；③ 落在所有块之外 ⇒ 记 `unmapped`，
不参与恒等式但**计入报告**（静默丢弃会让「验了几条/漏了几条」看不见）；
④ 命中多个块（区间重叠，正常不该发生）⇒ 取**最早**那个并记 `overlapped`。

顺带证实：**`clean` 本身就是 1:N**（实测块 6 → 字幕 7/9/10），旧口径在它上面
同样恒不可得 —— 这个缺口原本比「只有 long/real 有问题」更广。

## D3 · 跨会话 CER **存在波动** ⇒ 部分格的单次观测不可复现（`clean` / `fast` / `multi` / `long`）

| 项 | 值 |
|---|---|
| 状态 | ⏸ **已登记缺口，未修**（2026-10-11 判定；属素材/模型特性，非代码缺陷）<br>📌 **量化已补齐**：V6-5（2026-10-16）对七格各重复 N 次（短样本 5、long/real 3，共 **31 次观测**），区间见 `WER_REPORT_PLAN.md` **§7.6**；本条仍保留为**缺口登记**（波动成因未定位、非代码缺陷） |
| 严重度 | 中 —— 不产生错误结论，但**使「跨会话对拍」对这几格失效**，基准数字只能当「一次观测」 |
| 发现于 | #175 阶段3 七格重跑（与 P2 #173 对拍时） |

> **本条就是「跨会话 CER 存在波动」的正式记录。** 一句话结论：
> **同一份代码在两个会话上跑，CER 可以不同**（实测最大相对变化 **+64.3%**）。
> 因此 §7.1 / §7.2 里这几格的数字是**一次观测**，不是稳定基准。
> 按 2026-10-11 用户裁决：**这几格不标记为失败**，波动作为独立已知缺口在本条登记。

### 一、跨会话 CER 波动幅度（实测，本缺口的核心量化）

| 场景 | P2 会话（旧码） | 本会话（新码） | 本会话（旧码） | 波动幅度 | 相对变化 | 可复现？ |
|---|---|---|---|---|---|---|
| lowvol | 0.1715 | 0.1715 | **0.1715** | **0.0000** | 0% | ✅ |
| noise | 0.1821 | 0.1821 | **0.1821** | **0.0000** | 0% | ✅ |
| real | 0.1985 | 0.1985 | **0.1985** | **0.0000** | 0% | ✅ |
| clean | 0.1662 | 0.1504 | **0.1504** | 0.0158 | −9.5% | ❌ |
| long | 0.2589 | 0.2845 | **0.3053** | 0.0464 | +17.9% | ❌ |
| multi | 0.6834 | 0.628 | **0.6675** | 0.0559 | −8.2% | ❌ |
| fast | 0.2586 | 0.4248 | **0.4248** | **0.1662** | **+64.3%** | ❌ |

（波动幅度＝上表三列的 `max − min`；相对变化＝相对 P2 列。全部取自
`packaging/eval/p2_173_rt_*.json` / `p2_175_rt_*.json` / `p2_175_ctrl_*.json`。）

**读法与常见误用**：

- ✅ 正确：`noise` / `lowvol` / `real` 三格**三列逐位一致** ⇒ 可作稳定基准、可跨会话对拍。
- ❌ 错误：把 `fast` 的 `0.4248` 与 P2 的 `0.2586` 之差（0.1662）当成「质量下降」——
  它是**同一份旧代码在两个会话上的波动**，与任何代码改动无关。
- ⚠️ 注意方向：`clean`（−9.5%）与 `long`（+17.9%）**方向相反** ⇒ 不是单向系统性偏差，
  不能用「整体偏乐观 / 偏悲观」来解释。

### 二、判据：用**同一份代码**在两个会话上跑，看能不能复现

判定「不可复现」的**充分证据**是 **`旧码在本会话给不出 P2 的值`**。
`新码本会话 == 旧码本会话` 只证明**改动惰性**，**不能**证明跨会话可复现
（`fast` 即反例：同会话两码都 `0.4248`，但 P2 的旧码给 `0.2586`）。

### 三、`multi` 的直接证据（同会话，新旧码各 3 次）

| 代码 | 3 次 CER | 3 次 段→字 |
|---|---|---|
| 新码（#175） | 0.6675 / 0.6675 / **0.7599**（极差 **0.0924**） | 5 / 5 / 7 |
| 旧码（改动前） | 0.6675 / **0.6834** / 0.6675（极差 **0.0159**） | 5 / 9 / 5 |

**同代码同会话就不收敛**，且旧码自己就能给出 P2 的 0.6834 与另一个值
⇒ 这几格的「新码 CER ≠ P2 CER」**信息量为零**，既不能判漂移也不能判回归。

### 四、影响与用法

- **对拍纪律**：先跑「同会话新旧码对照」；只有当旧码在本会话**复现**了 P2 值，
  跨会话对拍才有效。否则跨会话类判据（CER / 字幕数）**整类作废**。
- **两类量要分开看**：**内容量**（CER / 识别文本）在**可复现格**上跨会话稳定
  （noise/lowvol/real 逐位一致），在**不可复现格**上不稳定；
  **时序量**（收尾 / p95）**所有格**都随会话单调漂移（实测 ≈ **+0.2s/会话**，见 §15.6）。
- **基准用法**：`clean` / `fast` / `multi` / `long` 的 §7 数字只作「一次观测」，
  **不得当稳定基准**；要用就得先做同格重复 N 次取分布（→ v3.5.0 `V5-6`）。

### 五、缺口

- ✅ **已补（V6-5，2026-10-16）**：**全 7 格「同代码同会话重复 N 次」系统性测量已做完** ——
  短样本格各 5 次、`long`/`real` 各 3 次，合计 **31 次观测**，散布区间已给出
  （见 `WER_REPORT_PLAN.md` §7.6）。结论：`noise`/`lowvol`/`fast` **确定性**（极差 0）；
  `clean`/`multi`/`long`/`real` 有区间（`multi` 极差 0.1979 最大）；
  `fast` 的 §7.1 单次值 0.2586 与五次重复的 0.4248 **完全不相交** ⇒ +64.3% 有了完整证据。
- ❌ 未定位「为什么 `multi`/`fast` 会走不同解码路径」——疑与实时喂入下的调度抖动
  + `condition_on_previous_text=True` 的自强化有关，但**未证实**，不下结论。
  （V6-5 已把该疑点的**对照实验**降为低成本项，列在 `plan_v6.md` §3.1「可选加强」，本轮未做。）
- ✅ **已补（V6-5，2026-10-16）**：`long` / `real` 的多次重复已测（各 3 次，单次 ≈10.5 min）。
  新增两条归因：`clean #2` 是**喂入侧偶发长阻塞**（≈200 s 整体偏移）、`real_3` 是**管道故障**（丢片 15），
  两者都**不是 ASR 质量问题** ⇒ 判定"异常"与"不可对拍"必须分开。
- ❌ 未验证「换台机器 / 换冷却状态」是否改善可复现性。

### 一、为什么必须用真人素材

口音是 7 个场景里**唯一无法合成**的：TTS 讲稿 + 劣化算子只能造出 clean/noise/lowvol/fast/multi，
造不出「带口音的普通话」—— 合成集全是**同一个 TTS 音源**经信号处理劣化，
无口音、无口误、无混响，测不出「口音」这个变量。

### 二、CER 0.4653 是全表最高，但**这是场景属性不是缺陷**

归因可量化（`normalize()` 后的口径）：参考稿含「函数」**18** 次，识别侧把该词族听错 **18** 次

## D5 · `auto` 口径下英文短语层仍注入中文课 ⇒ 用字错误 + CER **+0.288**

| 项 | 值 |
|---|---|
| 状态 | ✅ **已关闭**（代码层 2026-10-11 `V5-8`；**打包验证 2026-10-12 v3.5.0 阶段C 真机 e2e 通过**） |
| 严重度 | **高** —— 命中**默认路径**（`language="auto"` 是前后端 6 处默认值），CER 代价 **+0.2876（相对 +65.7%）** |
| 发现于 | V5-1 的 2×2 正交分解（`packaging/eval/v5_1_ab_*.json`，见 `WER_REPORT_PLAN.md` §7.4） |
| 影响文件 | `backend/dictionary/terminology.py:242/245/298`（分流条件）+ `backend/asr/pipeline.py`（构建时机） |
| 关闭证据 | [`WER_REPORT_PLAN.md`](./WER_REPORT_PLAN.md) **§16.3**（七格 × {zh, auto} 实测：**两格实际生效的提示词逐项相同**）+ **§16.4**（真机 e2e 的 C4） |

### 一、现象

同一份 clean 素材、同一个修复后的引擎，只改术语层语种：

| 术语层 | CER | edits | hypUnits | 繁体字符 |
|---|---|---|---|---|
| `auto`（**生产默认**） | **0.438** | 166 | 487 | 4 |
| `zh` | **0.1504** | 57 | 375 | **0** |

差 **+0.2876**。且 `hypUnits` 从 375 涨到 487 —— 不是"听漏"，是**多吐了 91 个字的乱码**。
实际输出里能看到复读式幻觉：`《卷机神经》,《卷机神经》×4`、`我们成为common ocean×4`。
残留的 4 个繁体字全是「捲」（应为「卷积」，模型写成「捲击」）—— 属**用字错误**，
在 `zh` 口径下为 **0**，证明它由本缺口造成，**不是** D1 的简繁路径没生效。

### 二、根因：`auto` 没有继承「缺陷 b」的修复

`_PHRASES_LAYER_EXCLUDED_LANGS = {"zh","yue","wuu","cmn"}`（`terminology.py:242`）——
中文语种不产出词表短语层，这是 2026-10-08 修「缺陷 b」时定的。
但 `language="auto"` **不在排除集合里**，于是默认路径继续注入 60 个英文多词短语。

原代码里写明了为什么当时不动 `auto`（`terminology.py:298`）：

> `language="auto"` 时**保持旧行为**（产出短语层）—— 不能因为要修中文课就把
> 英文课的既有能力一起关掉；且 **auto 下引擎会自行检测语种，此刻无法预判**。

🔴 **最后半句的前提已被 V5-1 消除**：引擎现在**在解码前**就会探测出语种
（`WhisperEngine._resolve_language()`，实测置信 0.9978）。
"此刻无法预判"不再成立 ⇒ 这个例外的理由消失了。

### 三、修法（已实施，2026-10-11）

引擎在探测判定为目标语种后回调管道，用**解析出的语种**重建术语层并热更新
（复用既有的 `set_initial_prompt()` 通路）。

落点三处，缺一不可：

| 文件 | 改动 |
|---|---|
| `backend/asr/whisper_engine.py` | 新增 `on_language_decided` 参数与 `_notify_language_decided()`；在 `_resolve_language()` 判定目标语种处调用，**只回调一次**、异常吞掉 |
| `backend/asr/pipeline.py` | 新增 `_terminology_language()` / `_rebuild_terminology()` / `_on_language_decided()`；`update_terminology()` 改为走同一来源 |
| `backend/asr/pipeline.py` | 新增 `make_term_rebuilder()`：给不构造完整管道的调用方（A/B 脚本）**复用同一个方法体**，避免两份实现静默漂移 |

**回调点选在 `_resolve_language()` 里而不是 `_transcribe()` 末尾**：引擎在**解码前**
回调 ⇒ `set_initial_prompt()` 写下的分层会被紧接着的 `_build_prompt()` 读到
⇒ 被判为中文的**第一块**就不带英文短语层，而不是从第二块才开始修。

**修复效果（同会话 A/B，`clean` 实时口径，2026-10-11）**：

| 条件 | 命令 | CER | edits | hypUnits/refUnits | 术语层重建 | 繁体字 |
|---|---|---|---|---|---|---|
| 修复前 | `--language auto --no-lang-aware-terms` | 0.3641 | 138 | 450/379 | — | 0 |
| **修复后** | `--language auto` | **0.1504** | **57** | **375/379** | zh → phrases 0 项 | **0** |
| P2 基线口径 | `--language zh --term-language zh` | 0.1504 | 57 | 375/379 | — | 0 |

* 修复幅度 **ΔCER −0.2137（−58.7%）**，`hypUnits` 450→375（少吐 75 个字的幻觉）；
* **修复后的默认路径与显式 `zh` 逐位一致**（CER / edits / hypUnits 三项全同）；
* `--language zh` 一列与 P2 时点完全一致 ⇒ v4 判据的对拍基准未受影响
  （显式语种不触发探测，回调根本不发）。
* ⚠️ `v58_off` 在本会话是 **0.3641**，而 V5-1 那次 A/B 里同一条件是 **0.438** ——
  这是台账 **D3** 的跨会话 CER 波动，所以本表的结论只能**同会话内部**比较。

| 项 | 值 |

### 一、现象

L4 首跑（`report-v350.json`）4 个 critical 步骤失败：

| 步骤 | 实测 |
|---|---|
| `界面加载完成`（critical） | **150s 内未出现** |
| `150s 稳定性`（critical） | **进程 0 个**（35 次采样全 0）；`/api/ping` **0/35（0.0%）** |
| `S层·悬浮窗自动恢复`（critical） | 90s 内未见「悬浮窗已显示 / 页面加载完成」 |
| `S层·IPC 心跳链路`（critical） | 未见「心跳链路已通」，渲染进程根本没发出心跳 |

即：安装成功、主进程进入了 GUI（`启动进入 GUI 主进程` = OK、后端一度 `就绪`），

### 二、证据链（`packaging/verify/app-stdio.log`，run-1）

```
15:48:40.499 [INFO]  [env] 运行模式=标准模式
15:48:42.255 [INFO]  [backend] 就绪: http://127.0.0.1:57291
15:48:51.903 [INFO]  [onboarding] 向导已打开

15:48:56.275 [INFO]  [watchdog] 页面 12s 内未完成加载，判定为 Chromium 沙箱被系统策略拦截，以兼容模式（--no-sandbox）重启

```

`[single-instance] 检测到第二次启动，将已有窗口提到前台` 这行**只能**由
`app.on('second-instance')`（`main.cjs:1779`）打出，而它在 Electron 里的触发条件是
**「另一个实例调用 `requestSingleInstanceLock()` 失败」** ⇒ **确定性证明：刚被拉起的兼容模式子进程抢锁失败。**

### 三、根因（代码）

`frontend/electron/main.cjs` 的启动恢复路径：

```js
// main.cjs:131 —— 无条件抢锁（除非 TINGKEBANLV_ALLOW_MULTI=1）
singleInstanceOwner = app.requestSingleInstanceLock();
if (!singleInstanceOwner) {
  console.log('[single-instance] 检测到已有实例在运行，本次启动直接退出');  // ← stdio 被 ignore，看不见
  app.quit();
}

// main.cjs:~1385 —— watchdog 回调
if (!relaunchInCompatMode()) { dialog.showErrorBox(...); }
app.quit();                    // 🔴 在 spawn 之后才 quit，且 app.quit() 是**异步**的

// relaunchInCompatMode() 内部
spawn(process.execPath, args, { detached: true, stdio: 'ignore', env: process.env })
```

**时序**：父进程（已崩溃但**仍持有锁**）→ spawn 子进程 → 子进程立刻 `requestSingleInstanceLock()` →
**失败**（父进程尚未 `quit` 完成）→ 子进程走 `main.cjs:135` 直接退出（它的 stdout 被 `stdio:'ignore'` 吞掉，
**日志里一个字都没有**）→ 父进程随后 `app.quit()` → **两个实例都没了**。

`stdio:'ignore'` + 父进程不弹框（`relaunchInCompatMode()` 返回了真 pid，所以 `dialog.showErrorBox` 不触发）
⇒ 用户感知是**「双击图标闪一下就没了」，且没有任何提示**。

# D7 · 网页用户测试暴露的四个连锁缺陷（2026-10-29，**未关闭**）

> **性质**：这四个缺陷**互相触发**，构成一条「假成功 → 进程崩溃 → 无限重连」的链。
> 桌面版同样受影响（前端与后端代码是同一份）⇒ **必须随下一版修复并重跑 L4 + e2e**。
> **发现方式**：网页用户测试（MIT 6.034 英文课 + B 站视频，真实使用场景）。
> **发现者**：用户在界面上只看到「已连接但没有字幕」，四个环节全部静默失败。

## 七之一、现象链

| # | 缺陷 | 表现 | 为什么难发现 |
|---|---|---|---|
| ① | 前端 `fetch` **不检查 `res.ok`** | 后端返回 4xx/5xx 也走 `.then()` ⇒ 显示「已连接 / 识别中...」而**后端根本没起管道** | 假成功，没有任何错误提示 |
| ② | `disconnectASR` 的 stop 是 **fire-and-forget**，`_startBackendASR` 紧接着 start | 两个管道短暂并存 | 时序竞态，偶发 |
| ③ | 两个采集线程**同一毫秒枚举音频设备** | PortAudio **断言失败 → abort 整个后端进程**<br>`Assertion failed: hostApi->info.defaultOutputDevice < hostApi->info.deviceCount` | C 层断言，Python 层**拿不到异常**（进程直接死） |
| ④ | 后端崩 ⇒ 前端 poll 失败 ⇒ `_tryReconnect` 指数退避重连 | **雪崩**：每次重连又多起一个管道 ⇒ 又触发 ③ | 前端把「服务挂了」当「网络抖动」 |

## 七之二、已实施的修法（**改了进包区 ⇒ 必须重新打包 + 重跑 L4/e2e**）

| 文件 | 改动 |
|---|---|
| `frontend/src/stores/useSubtitleStore.ts` | ① 检查 `res.ok`；**409（设备被占）不重连**；**先 stop 再 start 串行化**（消掉 ② 的竞态） |
| `backend/audio/capture.py` | 设备枚举**加全局互斥锁 + 缓存默认回环索引**（消掉 ③ 的并发）；流被外部打断后**退避重试重建**（1→2→4→8s） |
| `backend/api/routes.py` | `/asr/start` 做成**全局单例**：音频设备只能被一个 ASR 用，第二个课程明确返回 **409** 并告知是哪门课占着 |
| `frontend/src/pages/CourseConfig.tsx` | 「后端不可达」与「没有 Loopback 设备」**分成两种状态**（原来一律显示「未检测到音频 Loopback 设备」⇒ **把人引去装虚拟声卡**，而真实原因是后端没起） |

## 七之四、残留缺口（**未关闭**）

  但**下一版必须带上并重新验证**。
- ⚠️ **重试上限 8 次仍偏小**：Chrome 独占设备时，实测退避到第 8 次仍失败
