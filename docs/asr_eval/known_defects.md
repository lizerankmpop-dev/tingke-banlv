### 一、现象

`language` 取默认值 `auto` 时，中文音频的识别输出是**繁体**：

| `--language` | 识别输出（前 40 字） |
|---|---|
| `auto` | `'同學們好,今天這節刻,我們來講戰機神經網絡,以及它背後最重要的訓練算法,反向傳播'` |
| `zh` | `'同学们好,今天这节课,我们来讲《卷机神经》网络,以及它背后最重要的训练算法,反向'` |

同一份音频、同一份参考文本，只因这个参数不同，CER 从 **0.1636** 变成 **0.5198**。

### 二、证据链

**① 判定条件**（`backend/asr/whisper_engine.py`）：

```python
SIMP_HINT = "以下是普通话的句子，请使用简体中文转写。"      # :195
SIMP_HINT_LANGS = frozenset({"zh", "zh-cn", "zh-tw"})        # :197  ← 不含 "auto"
```

注入点两处，都按同一个集合判断：

```python
self._echo = EchoCleaner(                                     # :267-269
    get_simp_hint() if (self.language or "").lower() in SIMP_HINT_LANGS else ""
)
hint = (                                                      # :922-926
    get_simp_hint() if (self.language or "").lower() in SIMP_HINT_LANGS else ""
)
```

⇒ `self.language == "auto"`（字符串，见 `:249` 赋值；`:604` 才把它折成 `None` 传给 Whisper）
时，`"auto" not in SIMP_HINT_LANGS` ⇒ **引导语根本不注入**。

**② 默认值四处都是 `auto`**：

| 位置 | 代码 |
|---|---|
| 前端新建课程表单 | `frontend/src/pages/CourseList.tsx:25` / `:42`（`language: 'auto'`） |
| 前端课程配置页 | `frontend/src/pages/CourseConfig.tsx:210` / `:224`（`course?.language \|\| 'auto'`） |
| 后端请求模型 | `backend/api/routes.py:68` / `:132`（`language: str = "auto"`） |
| 后端管道取配置 | `backend/asr/pipeline.py:64` / `:94` / `:149`（`course_config.get("language", "auto")`） |

⇒ 用户**不主动动那个下拉框**，走的就是 `auto`。

**③ 单变量对照**（同一素材 `synth_clean_short_zhlecture_cnn.wav`，`--terms on` 固定）：

| `--language` | `--term-language` | `termPromptSections.phrases` | `termPromptMd5` | `accuracy.cer` | 输出 |
|---|---|---|---|---|---|
| `auto` | `auto` | 60 | `0f5e8159…` | **0.5198** | 繁体 |
| `auto` | `zh` | 0 | `d41d8cd9…`（空串） | **0.4617** | 繁体 |
| `zh` | `auto` | 60 | `0f5e8159…` | **0.1900** | 简体 |
| `zh` | `zh` | 0 | `d41d8cd9…`（空串） | **0.1636** | 简体 |

**读数**：第 1 行与第 3 行的提示词 md5 **完全相同**（`0f5e8159…`），简繁却翻转
⇒ **`--language` 是主因，与短语层无关**。`--term-language` 只贡献次要伤害
（同样 `auto` 下 0.5198 → 0.4617；同样 `zh` 下 0.19 → 0.1636，量级 +0.03~0.06）。

**④ 与设计意图矛盾**（这是判断「遗漏 vs 取舍」的关键）：

`whisper_engine.py:194` 的注释写着：

> 但术语表可能为空（新课程、用户没选领域），所以**必须显式注入**这句，不能靠术语表顺带解决。

即设计意图是「任何情况下都要让简体中文出现在提示词里」。而 `auto` 恰恰是**最容易术语表为空**
的那条路径（新课程默认值），却没有注入 ⇒ **更像遗漏，不像有意取舍**。

### 四、影响面

- **谁**：用中文课程、且没手动改过「语言」下拉框的用户 —— 即默认路径上的绝大多数中文用户。
- **多严重**：字幕仍是**可读**的（繁体 ≠ 乱码），但：① 与用户输入的简体术语/笔记不一致；
  ② 逐字稿导出、术语高亮、生词本匹配都会因字形不同而**失配**；
  ③ 评估口径上，CER 会被字形差异吃掉 **+0.35 以上**，让「识别质量」看起来比实际差一倍。
- **不会影响**：英文 / 日文 / 韩文课程（`SIMP_HINT_LANGS` 本就该排除它们）。

### 五、修法候选与**最终采纳路线**

立项时列了 4 条候选，**最终采纳的是第 5 条（下面 e）** —— 前 4 条共同的死结是
「引导语必须在**解码之前**进 prompt，而语种要**解码之后**才能从 `info.language` 读到」，
所以只能在二者之间做取舍。e 用一次**前置的 encoder-only `detect_language()`** 把这个死结解开。

| # | 修法 | 代价 | 风险 | 采纳 |
|---|---|---|---|---|
| a | `auto` 时也注入引导语（把 `"auto"` 加进 `SIMP_HINT_LANGS`） | 一行 | **高** —— 英文课会被塞进一句中文，可能把输出带偏。**必须先用英文素材做对照**才能定 | ❌ 弃 |

## D2 · 延迟指标在 6/7 格上「不可得」——VAD 块 ↔ whisper 段的 1:N 结构性配对缺陷

| 项 | 值 |
|---|---|
| 状态 | ✅ **已关闭**（#175，2026-10-10 立项 / 2026-10-11 验证；口径为**新增**，旧口径保留作对照） |
| 严重度 | 中 —— 不产出错误数字，但让一个**度量方法学缺陷**伪装成「这批数据没有延迟」 |
| 发现于 | P2 #173 逐格基线（§14.6 已如实记账） |
| 影响文件 | `scripts/eval_asr_quality.py`（**不进安装包**，见 `write-boundary.md`） |

### 一、现象

`--realtime` 下延迟指标只在 `lowvol` 一格算得出，其余 6 格 `latency.p95` 落 `0.0` 占位：

| 场景 | 片段（VAD 块） | 字幕（whisper 段） | `paired` |
|---|---|---|---|
| clean / noise / fast | 6 | 10 / 9 / 8 | `False` |
| lowvol | 6 | 6 | **`True`** |
| multi | 6 | 10 | `False` |
| long | 56 | 82 | `False` |
| real | 63 | 86 | `False` |

### 二、根因：两个集合是 1:N，不是 1:1

- `Recorder.segments` 记的是 **VAD 语音块**（绑在 `VoiceActivityDetector(on_speech_segment=…)`）；
- `Recorder.subtitles` 记的是 **whisper 段**（`WhisperEngine.on_partial` 回调）。

一个 VAD 块里可以含好几个 whisper 段 ⇒ **字幕恒多于片段**（实测 6→10 / 56→82 / 63→86）。
旧实现要求 `len(segments) == len(subtitles)` 才配对 ⇒ **在原理上永远不可靠**，
`lowvol` 的 6→6 只是巧合。

⚠️ 旧注释把原因写成「一旦发生**合并降级**（多个片段并成一次识别），条数就不相等了」——
那是「字幕变**少**」的罕见方向，**把常态的结构性原因掩盖成了一个边缘机制**。

### 三、修法（已实施，纯新增）

`on_partial(text, words)` 本来就随文本交了词级时间戳（`WordTimestamp{word, start, end, confidence}`），
旧代码在 `Recorder.on_subtitle` 里把 `words` 丢掉了。新增**不依赖配对**的口径：

```
latency_word_based = pushWall − (feed_t0 + audioWordsEnd)
```

- 锚点从「所属 VAD 块结束」换成「**这条字幕自己最后一个词的结束**」⇒ 不需要配对，7 格全部算得出；
- 旧字段 `latency` 与 `pair()` **一字未动**，仍按 1:1 输出，供对照；
- 无数据时给 `None`，**不用 `0.0` 占位**（0.0 会把「算不出来」读成「延迟极小」）。

**定义性恒等式**（两套口径唯一的差别）：

```
latency_新 − latency_旧 == seg.audioEnd − audioWordsEnd >= 0
```

VAD 块尾通常挂着静音 ⇒ 新口径恒 ≥ 旧口径，差值恰是静音尾巴长度。
实测 `lowvol` **6/6 条残差 0.0000**，六条尾巴 `1.276 / 0.564 / 1.516 / 0.760 / 0.356 / 0.932`。
恒等式可**从报告独立重算**（`segmentDetail` ⊕ `latency_word_based.detail`，都已落盘）。

### 五、残留缺口（明确未关闭）

- ❌ **`long` / `real` 两格的恒等式不可校验**：它们 `paired=False`，旧口径没有明细可比。

## D3 · 跨会话 CER **存在波动** ⇒ 部分格的单次观测不可复现（`clean` / `fast` / `multi` / `long`）

| 项 | 值 |
|---|---|
| 状态 | ⏸ **已登记缺口，未修**（2026-10-11 判定；属素材/模型特性，非代码缺陷） |
| 严重度 | 中 —— 不产生错误结论，但**使「跨会话对拍」对这几格失效**，基准数字只能当「一次观测」 |
| 发现于 | #175 阶段3 七格重跑（与 P2 #173 对拍时） |

> **本条就是「跨会话 CER 存在波动」的正式记录。** 一句话结论：
> **同一份代码在两个会话上跑，CER 可以不同**（实测最大相对变化 **+64.3%**）。
> 因此 §7.1 / §7.2 里这几格的数字是**一次观测**，不是稳定基准。
> 按 2026-10-11 用户裁决：**这几格不标记为失败**，波动作为独立已知缺口在本条登记。

### 一、跨会话 CER 波动幅度（实测，本缺口的核心量化）

| 场景 | P2 会话（旧码） | 本会话（新码） | 本会话（旧码） | 波动幅度 | 相对变化 | 可复现？ |
|---|---|---|---|---|---|---|
| lowvol | 0.1715 | 0.1715 | **0.1715** | **0.0000** | 0% | ✅ |
| noise | 0.1821 | 0.1821 | **0.1821** | **0.0000** | 0% | ✅ |
| real | 0.1985 | 0.1985 | **0.1985** | **0.0000** | 0% | ✅ |
| clean | 0.1662 | 0.1504 | **0.1504** | 0.0158 | −9.5% | ❌ |
| long | 0.2589 | 0.2845 | **0.3053** | 0.0464 | +17.9% | ❌ |
| multi | 0.6834 | 0.628 | **0.6675** | 0.0559 | −8.2% | ❌ |
| fast | 0.2586 | 0.4248 | **0.4248** | **0.1662** | **+64.3%** | ❌ |

（波动幅度＝上表三列的 `max − min`；相对变化＝相对 P2 列。全部取自
`packaging/eval/p2_173_rt_*.json` / `p2_175_rt_*.json` / `p2_175_ctrl_*.json`。）

**读法与常见误用**：

- ✅ 正确：`noise` / `lowvol` / `real` 三格**三列逐位一致** ⇒ 可作稳定基准、可跨会话对拍。
- ❌ 错误：把 `fast` 的 `0.4248` 与 P2 的 `0.2586` 之差（0.1662）当成「质量下降」——
  它是**同一份旧代码在两个会话上的波动**，与任何代码改动无关。
- ⚠️ 注意方向：`clean`（−9.5%）与 `long`（+17.9%）**方向相反** ⇒ 不是单向系统性偏差，
  不能用「整体偏乐观 / 偏悲观」来解释。

### 二、判据：用**同一份代码**在两个会话上跑，看能不能复现

判定「不可复现」的**充分证据**是 **`旧码在本会话给不出 P2 的值`**。
`新码本会话 == 旧码本会话` 只证明**改动惰性**，**不能**证明跨会话可复现
（`fast` 即反例：同会话两码都 `0.4248`，但 P2 的旧码给 `0.2586`）。

### 三、`multi` 的直接证据（同会话，新旧码各 3 次）

| 代码 | 3 次 CER | 3 次 段→字 |
|---|---|---|
| 新码（#175） | 0.6675 / 0.6675 / **0.7599**（极差 **0.0924**） | 5 / 5 / 7 |
| 旧码（改动前） | 0.6675 / **0.6834** / 0.6675（极差 **0.0159**） | 5 / 9 / 5 |

**同代码同会话就不收敛**，且旧码自己就能给出 P2 的 0.6834 与另一个值
⇒ 这几格的「新码 CER ≠ P2 CER」**信息量为零**，既不能判漂移也不能判回归。

### 四、影响与用法

- **对拍纪律**：先跑「同会话新旧码对照」；只有当旧码在本会话**复现**了 P2 值，
  跨会话对拍才有效。否则跨会话类判据（CER / 字幕数）**整类作废**。
- **两类量要分开看**：**内容量**（CER / 识别文本）在**可复现格**上跨会话稳定
  （noise/lowvol/real 逐位一致），在**不可复现格**上不稳定；
  **时序量**（收尾 / p95）**所有格**都随会话单调漂移（实测 ≈ **+0.2s/会话**，见 §15.6）。
- **基准用法**：`clean` / `fast` / `multi` / `long` 的 §7 数字只作「一次观测」，
  **不得当稳定基准**；要用就得先做同格重复 N 次取分布（→ v3.5.0 `V5-6`）。

### 五、缺口

- ❌ **未做全 7 格的「同代码同会话重复 N 次」系统性测量**：`multi` 做了 3+3 次、
  `clean` 做了 4 次（均新码）；其余各格只有**同会话旧码对照 1 次**
  （`packaging/eval/p2_175_ctrl_<场景>.json`），**散布区间未测** ⇒ 只能判「能否复现」，
  给不出「复现到什么程度」（→ v3.5.0 `V5-6`）。
- ❌ 未定位「为什么 `multi`/`fast` 会走不同解码路径」——疑与实时喂入下的调度抖动
  + `condition_on_previous_text=True` 的自强化有关，但**未证实**，不下结论。
- ❌ 未测 `long` / `real` 的多次重复（单次成本 ≈ 10.5 min，重复 N 次代价高，本轮未做）。
- ❌ 未验证「换台机器 / 换冷却状态」是否改善可复现性。

### 一、现象

> `language="auto"` 时**保持旧行为**（产出短语层）—— 不能因为要修中文课就把
> 英文课的既有能力一起关掉；且 **auto 下引擎会自行检测语种，此刻无法预判**。

🔴 **最后半句的前提已被 V5-1 消除**：引擎现在**在解码前**就会探测出语种

落点三处，缺一不可：

| 文件 | 改动 |

| `backend/asr/whisper_engine.py` | 新增 `on_language_decided` 参数与 `_notify_language_decided()`；在 `_resolve_language()` 判定目标语种处调用，**只回调一次**、异常吞掉 |

| `backend/asr/pipeline.py` | 新增 `make_term_rebuilder()`：给不构造完整管道的调用方（A/B 脚本）**复用同一个方法体**，避免两份实现静默漂移 |

回调 ⇒ `set_initial_prompt()` 写下的分层会被紧接着的 `_build_prompt()` 读到
⇒ 被判为中文的**第一块**就不带英文短语层，而不是从第二块才开始修。

### 一、现象

L4 首跑（`report-v350.json`）4 个 critical 步骤失败：

| 步骤 | 实测 |
|---|---|
| `界面加载完成`（critical） | **150s 内未出现** |
| `150s 稳定性`（critical） | **进程 0 个**（35 次采样全 0）；`/api/ping` **0/35（0.0%）** |

### 二、证据链（`packaging/verify/app-stdio.log`，run-1）


`[single-instance] 检测到第二次启动，将已有窗口提到前台` 这行**只能**由
`app.on('second-instance')`（`main.cjs:1779`）打出，而它在 Electron 里的触发条件是
**「另一个实例调用 `requestSingleInstanceLock()` 失败」** ⇒ **确定性证明：刚被拉起的兼容模式子进程抢锁失败。**

### 三、根因（代码）

`frontend/electron/main.cjs` 的启动恢复路径：

```js
// main.cjs:131 —— 无条件抢锁（除非 TINGKEBANLV_ALLOW_MULTI=1）
singleInstanceOwner = app.requestSingleInstanceLock();
if (!singleInstanceOwner) {
  console.log('[single-instance] 检测到已有实例在运行，本次启动直接退出');  // ← stdio 被 ignore，看不见
  app.quit();
}

// main.cjs:~1385 —— watchdog 回调
if (!relaunchInCompatMode()) { dialog.showErrorBox(...); }
app.quit();                    // 🔴 在 spawn 之后才 quit，且 app.quit() 是**异步**的

// relaunchInCompatMode() 内部
spawn(process.execPath, args, { detached: true, stdio: 'ignore', env: process.env })
```

**时序**：父进程（已崩溃但**仍持有锁**）→ spawn 子进程 → 子进程立刻 `requestSingleInstanceLock()` →
**失败**（父进程尚未 `quit` 完成）→ 子进程走 `main.cjs:135` 直接退出（它的 stdout 被 `stdio:'ignore'` 吞掉，
**日志里一个字都没有**）→ 父进程随后 `app.quit()` → **两个实例都没了**。

`stdio:'ignore'` + 父进程不弹框（`relaunchInCompatMode()` 返回了真 pid，所以 `dialog.showErrorBox` 不触发）
⇒ 用户感知是**「双击图标闪一下就没了」，且没有任何提示**。

### 四、为什么判定「不是 v3.5.0 版本回归」（三条独立证据）

| # | 证据 |
|---|---|

### 五、环境变化（为什么今天才暴露）

| 次 | 包 | 渲染器状态 | 150s 稳定性 | 结论 |
|---|---|---|---|---|
| 2026-10-10（历史基线） | v3.4.1 | **一次启动成功** | 6 进程 / ping 68/68 | 通过（59 步 / 57 OK） |
| 2026-10-12 | v3.4.1（归档包复跑） | 触发兼容降级 | 5 进程 / ping 64/64 | 通过（61 / 58） |
| 2026-10-12 | v3.5.0（首跑） | 触发兼容降级 | **0 进程 / ping 0/35** | **阻断 1**（62 / 55） |
| 2026-10-12 | v3.5.0（复跑） | 触发兼容降级 | 5 进程 / ping 64/64 | 通过（61 / 58） |
| 2026-10-12 | v3.5.0（`ALLOW_MULTI=1`） | 触发兼容降级 | 正常 | 通过（验证最小修法） |

⇒ 10-10 那次渲染器**根本没崩**（`一次启动成功`），所以降级路径**一次都没走到**；
10-12 本机的 Chromium 沙箱拦截状态变了（`渲染器状态` 从「一次启动成功」变成「触发了兼容模式降级重启」），
这条路径**首次被真正走到**，竞态因此首次暴露。
⚠️ 也就是说：**v3.4.1 基线里那句「L4 0 阻断」是在一条没被走到的路径上取得的**，
与今天的数字**不同口径**，不能直接对比。

### 七、缺口（明确未确认）

- ❌ **未在真机复现**：本机是**必然降级**的环境（沙箱 100% 被拦），竞态在这里被放大；
  真实用户机只有在沙箱被安全策略拦截时才会走到这条路径 ⇒ 实际命中率**未知**。
- ❌ 未量化竞态的**概率**：目前只有「1 次失败 / 3 次成功」这一组观测，
  不足以给出发生率（样本太小，**不下结论**）。
- ❌ 未验证修法 a 的**副作用**：放开子进程的单实例检查后，若用户恰好同时双击两次图标，
  是否会短暂出现两个实例（预期不会：只有 watchdog 拉起的那个子进程带该变量）。
