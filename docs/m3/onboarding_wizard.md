## 一、为什么需要首启向导

当前应用存在一个明确的「知识断层」，且**代码里没有任何新手引导**（已核实：全仓库无
`onboarding` / `firstRun` / `welcome` 相关实现）。

断层体现在四件事上，全部是用户**第一次就能撞上、但界面里没有解释**的：

| # | 断层 | 用户的第一反应 |
|---|---|---|
| 1 | 窗口会「缩小成悬浮条」，主界面看起来像是消失了 | 「软件是不是崩了？」 |
| 2 | 悬浮条默认**鼠标穿透**，点不动、拖不动 | 「这窗口卡死了？」 |
| 3 | 位置挪丢之后没有明显可见的补救入口 | 「拖到屏幕外面了，没办法了」 |
| 4 | 「术语提示词自动防循环降级」是一句技术黑话 | 「降级？降什么级？会不会影响识别？」 |

前三条属于**交互模型本身与直觉相反**，第四条属于**术语未翻译成收益语言**。这两类问题
都应该在「用户第一次打开软件」时一次性讲清楚，而不是等他踩坑后去翻 README。

第 4 条尤其重要：`termAutoDegrade` 默认开启，它在背后悄悄改变提示词预算。用户如果
不知道这件事，在专业术语密集的课上遇到「术语没识别出来」时，会得出完全错误的结论。

## 二、触发与状态存储

### 2.1 触发条件

```
首次启动（overlay.json 不存在 / 无 onboarding 记录）→ 弹出向导
```

存储位置：`<userData>/onboarding.json`

> ⚠️ **实现偏离（已按实际项目结构落地）**：实际存放于 `dataHome()/onboarding.json`，
> 即与 `overlay.json`、`logs/electron.log` 同级（默认 `~/.tingkebanlv`，可用
> `TINGKEBANLV_HOME` 环境变量覆盖）—— **不是** `%APPDATA%/听课伴侣/`。
> 设计稿当时把「userData」与「现有状态目录」当成了同一个位置，实际项目里全部状态
> 一直在 `dataHome()`。决定性理由：冒烟脚本与实装验证都靠 `TINGKEBANLV_HOME` 把
> 状态隔离到临时目录；若改用 `app.getPath('userData')`，跑一次冒烟就会读到
> **开发者本机真实的** onboarding 状态（向导不弹、用例假通过），并把 `completed: true`
> 写进真实用户配置。见 `frontend/electron/onboarding-state.cjs` 顶部注释。

### 2.2 建议结构

```jsonc
{
  "schemaVersion": 1,
  "completed": false,        // 用户走完最后一步
  "dismissedAt": null,       // 用户点了「跳过」的时间戳（ISO 8601）
  "lastShownVersion": null,  // 预留：大版本更新后重新展示变更点
  "seenHotkeys": {}          // 预留：逐条提示的「知道了」状态
}
```

**设计原则**：

- `completed` 与 `dismissedAt` **都算「不再自动弹出」**，尊重用户跳过。
- 但必须留一个**可重现入口**（见 §7），否则用户跳过后永远找不回来。
- 写入必须是**原子写**（临时文件 + `rename`），复用 `overlay-settings.cjs` 里已验证的
  写盘模式 —— 该模块专门注释过「写到一半崩溃」这个用例。

### 2.3 何时**不应**弹出

- 兼容模式启动时（`COMPAT_MODE === true`）：此时渲染环境本身不稳定，再叠一个模态
  向导会放大故障面。建议兼容模式下**推迟**到用户手动触发。
- 后端尚未就绪时：向导第 3 步需要展示模型准备进度，等 `/api/ping` 通过再弹。

## 三、分步流程与文案

共 **6 步**。每步一个「为什么」+ 一个「怎么做」，禁止出现纯技术名词。

### 第 1 步 · 欢迎

```
标题：欢迎使用听课伴侣

正文：
  这是一款完全本地运行的听课助手。

  它能做到：
    · 把老师说的话实时转成字幕
    · 点字幕里的任意单词，立刻看到中文释义
    · 自动整理这节课的专业词汇

  全程不联网、不上传录音，你的课程内容只留在这台电脑上。

  [ 开始设置 ]        [ 跳过，直接使用 ]
```

> 「不联网、不上传」是核心信任点，必须放在第一屏。这也是与云端字幕产品区分最明显的一点
> （仅 Ollama 术语提取/讲解为可选联网能力，需在此处诚实标注 —— 见 §6 备注）。

### 第 2 步 · 选择使用场景

```
标题：你主要怎么听课？

  ┌──────────────────────────┬──────────────────────────┐
  │  💻 在线网课              │  🏫 线下课堂              │
  │                          │                          │
  │  Coursera / B站 / YouTube │  教室 / 讲座 / 会议室      │
  │                          │                          │
  │  直接捕获电脑播放的声音     │  用麦克风收音             │
  │  识别语言以英文为主         │  中英文混合都能识别        │
  │  不需要任何额外设置         │  建议使用降噪麦克风        │
  └──────────────────────────┴──────────────────────────┘

  小贴士：电脑外放的声音可以直接采集，不需要装虚拟声卡，
         也不用改系统默认播放设备。

  [ 上一步 ]                              [ 下一步 ]
```

> **文案依据**：Windows 下 WASAPI 回环采集由 `PyAudioWPatch` 直接提供，
> 不需要 VB-Cable 之类的虚拟声卡。这是竞品/教程里最常见的错误前置步骤，
> 主动澄清能省掉大量用户求助。
>
> 选择结果写入课程创建时的默认类型，不写入全局配置 —— 用户可能两种场景都用。

### 第 3 步 · 准备语音模型

```
标题：正在准备语音模型

  首次使用需要准备好识别模型（已随安装包内置，约 141 MB）。
  这一步只在第一次启动时需要，之后就是秒开。

  进度：[████████░░░░░░░░]  准备中…

  ✓ 无需联网下载
  ✓ 无需你手动放置任何文件
```

**状态机（按后端真实信号驱动，不要用假进度条）**：

| 阶段 | 判据 | 显示 |
|---|---|---|
| 后端启动中 | `/api/ping` 未通 | 「正在启动本地服务…」 |
| 模型就绪 | 模型可用性探测通过 | 「✓ 模型已就绪」+ 自动跳下一步 |
| 模型不可用 | 三级链全部失败 | 降级为**可操作**错误（见下） |

**模型不可用时的文案**（必须给出可执行动作，不能只报错）：

```
  模型准备失败。

  请尝试：
    1. 关闭应用后重新打开（会自动重试）
    2. 若反复失败，点击下方按钮导出日志，反馈给开发者

  [ 重试 ]  [ 导出日志 ]  [ 先跳过，稍后再说 ]
```

> **实现依据**：模型种子存在三级查找链 ——
> `packaging/seed`（安装包内置）→ `resources/whisper_models`（只读）→
> `$HOME/whisper_models`（可写）。判可用只看 `ok` 字段，不看 `action`
> （`action` 可能是 `copied` 或 `reused`，都是成功）。向导必须复用同一判据，
> 不能自己另写一套探测逻辑。

### 第 4 步 · 认识悬浮字幕条（**最关键的一步**）

```
标题：字幕会变成一个「悬浮条」

  开始识别后，主界面会收起来，变成屏幕底部一条细长的字幕条。

  这个字幕条有三种状态，先认一下：

    ┌─────────────────────────────────────────┐
    │  ① 平时：鼠标穿透                        │
    │     点它、拖它都没反应 —— 这是故意的。     │
    │     这样它不会挡住网课页面上的按钮。       │
    ├─────────────────────────────────────────┤
    │  ② 要挪位置：按 Alt + Shift + D          │
    │     临时恢复鼠标操作，拖顶部紫色条即可。   │
    │     再按一次退出调整模式。                │
    ├─────────────────────────────────────────┤
    │  ③ 拖丢了：按 Alt + Shift + R            │
    │     一键挪回屏幕底部居中，一定会出现。     │
    └─────────────────────────────────────────┘

  随时按 Alt + Shift + O 可以显示 / 隐藏它。

  [ 上一步 ]                              [ 下一步 ]
```

> **设计依据**：这是整个产品最反直觉的交互 ——
> `OverlayControlPanel.tsx` 的注释里明确写了「悬浮窗鼠标穿透，本身就点不到，
> 自然也没法在主应用里模拟拖拽」。用户在第一次遇到「点不动」时如果没有人提前告知，
> 极大概率判定为故障。**必须前置解释，不能等用户发现。**
>
> ## 第 4 步是全向导的核心价值，其他步骤都可以砍，这一步不能砍。

### 第 5 步 · 全局热键速查

完整表（与 `frontend/electron/main.cjs` 的 `registerOverlayShortcuts()` 逐一对应）：

| 热键 | 作用 | 是否需要先打开悬浮窗 |
|---|---|---|
| `Alt + Shift + O` | 显示 / 隐藏悬浮字幕条 | — |
| `Alt + Shift + D` | 进入 / 退出调整模式（临时恢复鼠标操作） | 是 |
| `Alt + Shift + R` | 重置位置到屏幕底部居中 | 是 |
| `Alt + Shift + ]` | 字幕字号 +2 px | 是 |
| `Alt + Shift + [` | 字幕字号 −2 px | 是 |

```
标题：这五个快捷键，建议记一下

  它们在任何窗口里都能用 —— 包括你正在看网课的全屏浏览器。

  [表格：见上]

  如果某个快捷键没反应，通常是被别的软件占用了。
  应用不会报错，但可以在「导出日志」里查到是哪一条注册失败。
```

**权限说明（Windows）**：

> **结论：Windows 下注册全局热键不需要申请任何系统权限，也不会弹 UAC。**
>
> 这与 macOS 不同 —— macOS 上的部分全局快捷键能力需要「辅助功能」授权。
> 本项目主分发渠道为 Windows（NSIS 安装包），因此 Windows 路径下
> **不要**画蛇添足地写「请授予权限」的提示，那会引出一个并不存在的设置项。
>
> 唯一真实的失败原因是**热键被其它程序占用**（`globalShortcut.register`
> 返回 `false`）。此时应引导用户查日志，而不是引导用户去改系统设置。

`Alt + Shift + D` 组合在部分输入法（如某些五笔/日文 IME）下可能被抢占，
向导中可加一行灰色小字：

```
  提示：如果你常用输入法，「Alt + Shift」可能被系统占用。
       遇到这种情况请导出日志反馈，我们会更换默认组合。
```

### 第 6 步 · 术语识别（含自动降级开关的通俗说明）

这一步要同时完成两件事：**讲清术语的价值**，以及**讲清那个默认开启的降级开关**。

```
标题：让专业词也能被听懂

  老师讲的专业词，语音识别经常听错 ——
    convolution 被听成 convalution
    eigenvalue 被切成 eigen value

  你看到的字幕本身就是错的，查词自然查不到。

  听课伴侣用「三层术语」来修正这个问题：

    1. 你手动填的术语        ← 最重要，识别优先级最高
    2. 这节课已经识别出的词   ← 自动积累
    3. 内置领域术语表        ← 覆盖计算机 / 医学 / 物理 / 经济等 15 个领域

  你可以在创建课程时直接填核心词，也可以稍后在课程配置里补充。
```

**降级开关的通俗说明**（这一段的措辞是本节的核心产出）：

```
  ── 关于下面这个开关 ───────────────────────────────

  ☑ 术语提示词自动防循环降级          （默认开启，建议保持）

  它解决什么问题？

    术语表如果太长，识别引擎会「刹不住车」——
    开始重复输出同一句话，字幕越滚越多，识别也会变慢。

  它做了什么？

    一旦发现这种重复，自动把发给引擎的术语表缩小一些，
    让识别恢复正常。你已经积累的课程词汇**不会丢**。

  代价是什么？

    降级生效后，这一节课剩余时间里参与识别的术语会变少，
    可能有个别术语识别不出来。

  那要关掉它吗？

    一般情况下不用。如果你是术语密集型课程（比如整节课都在讲
    专业名词），并且宁可偶尔看到重复字幕，也要保住完整的术语识别，
    可以关掉它。
```

> **文案红线（实现时不得违反）**：
>
> 1. **禁止**出现「提示词」「token」「预算」「截断」「200 字符」这类实现细节。
>    用户不需要知道 `initial_prompt` 是什么。
> 2. **禁止**说「智能降级」「自适应优化」这类不承诺任何具体行为的话。
>    必须说清「什么时候触发、触发后会发生什么、代价是什么」。
> 3. **必须**说明「重新开始听课后会恢复完整术语表」—— 这是降级唯一的解除方式，
>    不说清楚用户会以为软件「坏了，一直恢复不了」。
>
> **⚠️ 与 P0-3 的一致性要求（重要）**：
> P0-3 已经把降级机制从「把提示词截断到 200 字符」改为「改用更小的 **token 预算**」
> （`PROMPT_TOKEN_BUDGET=220` → `DEGRADE_TOKEN_BUDGET=70`）。
>
> 这意味着：
> - 讨论这个开关时**不要**再提「200 字符」，那是已经废弃的实现。
> - 现有控制面板里「提示词已缩减到 N 字符」的提示语**已经与实现脱节**
>   （`termPromptChars` 计算的是原始提示词长度，降级后不再变化）。
>   详见 [`backlog_b1_b2_b3.md`](./backlog_b1_b2_b3.md) 的 **B4**。
> - 向导文案应该写成「参与识别的术语会变少」，不绑定任何具体数值 ——
>   这样以后调整预算参数时文案不用跟着改。

**可选：引导导入自定义术语表**

```
  ── 可选：导入你自己的术语表 ─────────────────────

  如果这门课有现成的词表（比如老师发的 PDF 讲义、上届学长整理的术语表），
  可以复制成每行一个词的文本直接粘贴进去，比一个一个手动加快得多。

  [ 我知道了 ]
```

> 现状核实：**后端目前没有「批量导入术语表」的接口**（只有 `custom_terms` 逐条写入）。
> 因此这一段文案应作为**可选项**实现 —— 若 M3 不打算做导入功能，
> 这段文案要**整段删除**，而不是写出来让用户去找一个不存在的按钮。
> 若要做，需要新增后端接口并按 §8 补冒烟用例。

## 四、UI 与排版规范

沿用应用现有设计语言（`OverlayControlPanel.tsx` 的 `styles` 已给出基准）：

| 项目 | 取值 | 依据 |
|---|---|---|
| 卡片宽度 | `400px`，`maxWidth: 92vw` | 与控制面板一致 |
| 卡片最大高度 | `86vh`，内容区 `overflow: auto` | 与控制面板一致 |
| 圆角 | `var(--radius)` | 全局变量 |
| 卡片背景 | `var(--bg-secondary)` | 与控制面板一致 |
| 主色 | `var(--accent)` / `var(--accent-light)` | 全局变量 |
| 正文字号 | `13px`，行高 `1.6` | 与控制面板 `rowLabel` 一致 |
| 辅助说明字号 | `11px`，颜色 `var(--text-muted)` | 与控制面板 `hint` 一致 |
| 遮罩 | `rgba(0,0,0,0.55)`，`zIndex: 300` | 与控制面板一致 |
| 图标 | `lucide-react`，步进图标 `16px` | 项目已用图标库 |

**新增要求**：

- 步骤指示器（`1 / 6` 或圆点），让用户知道还剩几步。
- 「跳过」按钮全程可见，不做「必须走完」的强制流程。
- 快捷键展示使用 `<kbd>` 语义化标签，便于后续做无障碍。
- **无障碍**：所有开关必须带 `role="switch"` 与 `aria-checked`
  （这正是 Backlog **B2** 要修的问题，新代码不要重复犯）。
- 对比度：正文与背景对比度 ≥ 4.5:1；`var(--text-muted)` 的 `11px` 小字仅用于辅助信息，
  不承载必要内容。

## 五、埋点与可观测性

向导本身应当可观测，否则「用户为什么还是不会用」无从判断。

建议记录到 `onboarding.json`：

```jsonc
{
  "startedAt": "…",
  "stepReached": 4,          // 走到过的最深步骤（关键指标：卡在哪一步）
  "completed": false,
  "dismissedAt": "…",
  "durationMs": 41200
}
```

同时打一条 `logLine` 到 `electron.log`：

```
[onboarding] 完成 步骤=6/6 耗时=41.2s
[onboarding] 跳过 步骤=4/6
```

> **为什么 `stepReached` 比 `completed` 更有用**：如果绝大多数用户都停在
> 第 4 步或第 5 步，说明那两步文案太长或信息密度过高，需要精简 ——
> 光看「完成率 30%」是得不出这个结论的。
>
> 这也直接呼应了本轮 A/B 复盘里的教训：**「没记」和「没查到」在报告里长得一模一样**
> （见 `ASR_Pipeline_Validation_Report.md` §6.12 埋点缺陷复盘）。
> 向导如果只记 `completed`，就等于放弃了定位体验瓶颈的能力。

## 六、备注：关于「完全本地」的措辞准确性

向导第 1 步承诺「全程不联网」，但需要**诚实标注**例外：

| 能力 | 是否联网 | 是否必需 |
|---|---|---|
| 语音识别（Faster-Whisper） | 否 | 是（核心） |
| 本地词表释义（ECDICT + 内置 3300+ 词） | 否 | 是 |
| AI 术语提取（Ollama + Qwen2.5） | 否（本地模型） | 可选 |
| AI 深度讲解 / 摘要 / 答疑 | 否（走本地 Ollama） | 可选 |
| 切换云端 LLM API | **是** | 可选 |

结论：**默认链路确实完全不联网**。但用户如果主动配置了云端 API，就会联网。
因此第 1 步的措辞建议微调为：

```
  默认全程本地运行、不联网。
  （只有当你主动配置了云端 AI 服务时才会联网，这个功能默认关闭。）
```

这样既保留了核心卖点，又不会在用户配置云端 API 后产生「被骗了」的感觉。

## 七、可重现入口（跳过后的找回路径）

用户跳过后必须能重新打开。建议放两处：

1. **帮助菜单 / 关于对话框**里：「重新查看新手引导」按钮 → 重置 `completed` 并重新弹出。
2. **首次创建课程**时，若 `completed === false`，在课程配置页顶部挂一条**非模态**提示条：

```
  第一次用？[ 花 1 分钟看下怎么用 ]   ×
```

> 第 2 点在交互上比强制模态更友好：用户此刻正在做「创建课程」这件真实的事，
> 引导嵌在这个上下文里比悬空的模态窗更容易被接受。

### 10.2 与设计稿的三处有意偏离

1. **存储位置**：`dataHome()` 而非 `userData`（理由见 §2.1 偏离说明）。
2. **兼容模式语义**：§2.3 的「推迟」实现为 `shouldShowWizard` 里 `force` 排最前 ——
   「重新查看引导」入口（force 语义）在兼容模式下**仍然可用**；`compatMode` 只拦截
   **自动**弹出。把 force 放到后面写，手动入口会静默失效且无报错。
3. **模态**：窗口 `parent: mainWindow` 但 `modal: false`。Windows 上 modal 会卡住
   主窗口关闭按钮，一旦向导页面渲染失败就是死锁。

### 10.3 语义约定（易错点）

- `onboarding:close`（右上角 ×）**不写任何标记**，下次启动仍会弹 —— 关闭窗口
  ≠ 拒绝引导；`onboarding:dismiss`（「跳过，直接使用」按钮）才写 `dismissedAt`。
- 主窗口被关闭时向导窗口随之销毁，**同样不写标记**（用户只是关了主窗口）。
- `stepReached` 只增不减，衡量「卡在哪」而不是「当前在哪」；跳过时保留步号。
- 第 3 步「进程没起来」与「模型没准备好」是**两句不同的话**，对应两个请求
  （`/api/ping` + `/api/asr/model-status`）而不是一个布尔；`!pingOk && attempts >= 60`
  判 `failed`，避免无限转圈。

### 10.4 文案红线（自动化守卫）

`tests/onboarding-copy.test.mts` 直接 import `onboarding.ts` 遍历全部字符串：

- 禁实现术语：`token / 预算 / 截断 / 提示词 / initial_prompt`（与 B4 后控制面板同口径）
- 禁不承诺行为的说法：`智能降级` 等
- 必须有恢复说明：`重新开始听课（停止识别再开始）就会恢复完整术语表`
- 热键表与 `main.cjs` 的 `bind('Alt+Shift+…')` **去空格对拍**（引导教错快捷键
  是用户无法自救的错误）
- 变异验证在进程内构造（往文案里塞禁词再跑审计），不需要临时改文件

### 11.4 验收中发现的两个缺陷

#### 缺陷 A（**已修复**）：安装包内后端不认识 `/api/asr/model-status`

- **现象**：向导第 3 步轮询该接口，安装包内返回 **404**。
- **根因**：`npm run electron:build` **不重建后端**（复用 `packaging/out/backend-server`，
  本机是 10-05 20:50 的构建），而 M3 才新增这条路由（`backend/api/routes.py:829`）。
- **修复**：用 venv PyInstaller 重建后端（`package.json` 里的 `backend:build` 用裸 `python`，
  本机没有 pyinstaller，必然失败）：
  `venv/Scripts/python.exe -m PyInstaller ../packaging/backend_server.spec --noconfirm --distpath ../packaging/out --workpath ../packaging/build`
  旧后端改名 `packaging/out/backend-server.preM3` 保留。重打安装包后接口实测 **200 OK**。
- **配套提醒**：只要 M3 之后动了 `backend/`，发布前**必须**单独重建后端，`electron:build` 不会做。

#### 缺陷 B（**已修复** — 复验见 §十二）：首启向导第 3 步必然显示「模型准备失败」

- **现象**：全新安装首启，第 3 步显示「正在准备语音模型 → **模型准备失败。**」，
  按钮为「重试 / 导出日志 / 先跳过，稍后再说」。等 60s 也不会自愈，**反复点「重试」也无效**。
- **根因链**：
  1. `model-status` 判据是 `check_installed(model, deep=False)`，检查的是**可写层**
     `model_root()` = `TINGKEBANLV_HOME/whisper_models`（`model_bootstrap.py:62`）。
  2. 安装包里模型只存在于**只读种子层** `resources/whisper_models`（142MB），
     **播种（`ensure_model`）只在 `whisper_engine` 加载模型时才发生**
     （`whisper_engine.py:367`）——即用户真正点「开始识别」时。
  3. 于是首启第 3 步探测时可写层为空 → `ok:false` → 前端 `modelPhase` 判 `'failed'`（终态）。
  4. 「重试」只重新探测，不触发播种 → 永久失败。
  5. 文案还引导「关闭应用后重新打开（会自动重试）」——**重启同样不会播种**，属无效引导。
- **注释与实现不一致（缺陷的证据）**：`frontend/electron/main.cjs:370-371` 注释写
  「后端首次启动时把它播种到 TINGKEBANLV_HOME/whisper_models」，但后端启动路径上
  并没有播种调用；主进程只通过 `TINGKEBANLV_SEED_MODEL_DIR` 把种子路径传下去。
- **影响面**：首启正常路径（走完 6 步）被阻断，用户只能点「先跳过，稍后再说」；
  且被误导去点无效的「重试」。**真实用户首次使用必然遇到。**
- **修复建议（三选一）**：→ **用户拍板选方案 A**（后端 `lifespan` 后台幂等播种 +
  前端状态机加 `seeding` 档）。实施与复验见 **§十二**。
  - **方案 A（推荐，改动最小）**：后端 `lifespan` 启动时**后台异步**幂等播种
    （`ensure_model` 本身幂等，已有 `has_verified_marker` 标记），
    `model-status` 在「播种中」时返回 `ok:false` 但前端应把「种子可用且正在播种」
    映射为 `preparing` 而非 `failed`。
  - **方案 B（最贴合设计稿）**：`model-status` 接口在探测失败且 `seed_available()` 为真时
    **自己触发一次后台播种**，并把状态机扩成三态（`preparing / ready / failed`）——
    接口契约要从 `{ok, model}` 扩一个字段，前端 `modelPhase` 同步调整。
  - **方案 C（仅文案）**：接口在前端探测失败但种子可用时仍返回 `ok:true`
    （首次识别时自愈，只是慢几秒），第 3 步不再显示失败。语义最弱，但有自愈能力。
- **测试盲区（本次逃逸的原因）**：`verify_install.py` 的「首启播种落盘」步骤之所以通过，
  是因为脚本在此之前跑了**后端 `--selftest`**，而 `selftest` 会调 `ensure_model`
  —— 等于**验收脚本替产品完成了播种**。修复缺陷 B 后，该步骤才真正验到「应用会播种」。
  在此之前不建议把该步骤当作有效证据。
  → **已于 §12.4 修掉**：原断言改名为「后端自检播种落盘（--selftest 触发，非应用行为）」
  并降为非关键，另加「清空工作副本 → 启动应用 → 断言模型自己长出来」三步正面断言。

### 11.5 待决策：第 6 步开关名与控制面板口径不一致（**已裁决：保留同源、不强制逐字一致**）

| 位置 | 首次验收时 | 现在 |
|---|---|---|
| 向导第 6 步（`onboarding.ts` `step6ToggleLabel`） | `参与识别的术语自动防循环` | 同左（未变） |

两条红线原本在打架：`tests/onboarding-copy.test.mts` 的**禁词守卫**要求文案不出现

#### 📌 永久约定（2026-10-07 用户裁决，后续改文案必须遵守）

> **约定：向导版本为精简版名称，控制面板增加「降级」后缀，二者为同一功能，
> 守卫校验核心短语，不强制逐字匹配；禁止 UI 文案出现「提示词」。**

即：

| 位置 | 正式名称 | 面向谁 |
|---|---|---|
| 向导第 6 步 | `参与识别的术语自动防循环` | 新用户：只讲核心功能概念，简洁为主 |
| 控制面板 | `参与识别的术语自动防循环` + `降级` | 高级设置：补充「降级」这个行为后果，用户能理解二者是同一个开关 |

裁决理由（原文要点）：

1. 向导面向新用户只讲核心概念，简洁为主；面板是**高级设置**，补「降级」说明行为后果，
   用户能理解二者是同一个开关。
2. 静态守卫维持现有逻辑：**校验核心短语存在、禁止「提示词」禁词、不强制全文完全匹配**
   —— 已足够防止引入内部工程术语。
3. 核心短语若被改掉，守卫仍能捕获；反之若强行删掉面板的「降级」，会**丢失对高级用户的
   行为说明**，收益很小。

守卫的落地形式见 §12.5（`frontend/tests/panel-copy.test.mts`）：断言面板与向导的可见名称
**都包含**核心短语 `参与识别的术语自动防循环`，并禁止 `提示词` / `initial_prompt`
（守卫本身带变异验证）。这是「同源」而不是「逐字相等」的自动化表达。

> 一般化教训：**多页面文案只保证核心语义同源，允许按场景微调后缀；用静态守卫拦截内部
> 工程术语，而不是强制所有页面一字不差。** 强制逐字相等会把「面向不同受众的措辞」也
> 一并禁掉，反而降低可读性与可维护性。

### 11.6 验收工具维护记录

- `scripts/verify_install.py`：修正过时断言 —— 原「迁移后设置保留」写死
  `schemaVersion == 3`，而 M3 已升到 **4**（`overlay-settings.cjs:16`），导致误报 FAIL。
  改为 `isinstance(int) and >= 3` + 文案去版本号。**教训：验收脚本里的版本号断言别绑死具体值。**
- `scripts/drive-onboarding.cjs`（新增）：CDP 驱动打包应用的 4 个 mode；
  踩到的三个坑已写进文件头注释 —— ① 第 3 步模型就绪后**自动跳步**，固定步数脚本必错位；
  ② `__reactProps.onClick` **绕过 DOM disabled**，会把「按钮不可点」误判成「用户点了」；
  ③ 点「开始使用」/「跳过」后主进程**立即关闭向导窗口**，之后所有 CDP 调用超时，
  截图必须安排在点击之前；另有一个隐蔽坑：CDP 截图响应可能是**二进制帧**，
  `JSON.parse` 抛错发生在事件回调里、外层 try 包不住，会静默带崩整个脚本。

## 十二、缺陷 B 修复与复验（2026-10-07）

> 本节是 §11 的续篇。§11 保留「首次验收 + 发现缺陷」的原始记录（以便对照缺陷是怎么
> 逃过第一轮的），这里是修复实现与复验结果。两节合起来才是完整的验收留痕。

### 12.1 修复方案（用户拍板：方案 A）

**方案 A：后端 `lifespan` 后台幂等播种 + 前端状态机区分「种子存在 / 正在播种 / 播种完成 / 失败」。**

选它的理由：最贴合本模块的原始设计意图 —— `model_bootstrap.py` 顶部的装配关系图
一直写着「首次启动播种」，但那个调用点**此前并不存在**（见 §11.4 根因链）。所以这不是
「新增一个机制」，而是**把注释里承诺的行为补上**。

三条设计约束（写在 `model_bootstrap.py` 的模块注释里，视为约束而非实现细节）：

| 约束 | 原因 |
|---|---|
| **必须后台线程** | 141MB 拷贝要几秒到几十秒（慢盘更久）。同步做会拖长后端就绪时间，而主进程是按日志里的「`[backend] 就绪`」标记解析端口的 —— 卡住等于整个应用起不来 |
| **必须幂等** | `ensure_model` 自己先 `check_installed`（毫秒级），且与引擎加载共用 `_copy_lock`：既不会重复拷贝，也不会和识别抢文件 |
| **失败不崩溃** | 异常与失败原因落在状态里、经 `/api/asr/model-status` 暴露给前端。播种失败不该让后端起不来 |

落地文件：

| 文件 | 改动 |
|---|---|
| `backend/asr/model_bootstrap.py` | 新增后台播种段：`seed_exists()` / `background_seed_state()` / `start_background_seed()`（幂等）/ `reset_background_seed_state_for_tests()`；失败原因映射为**稳定枚举**（`no-seed` / `io-error` / `integrity` / `unknown`），细节只进日志 |
| `backend/main.py` | `lifespan` 钩子里调用 `start_background_seed()`；`TINGKEBANLV_SKIP_BACKGROUND_SEED=1` 可关（测试与 `--selftest` 用） |
| `backend/api/routes.py` | `asr_model_status` 扩为四字段 `{ok, model, seed_exists, seeding, error}`；**兼作幂等触发点**（旧版本升上来的用户没跑过 lifespan，靠这里自愈） |
| `frontend/src/lib/onboarding.ts` | `ModelPhase` 加 `seeding` 档；新增 `SEED_TIMEOUT_ATTEMPTS = 90`（兜底「卡死」）；`phaseIsFinal` 保持只有 ready/failed 是终态 |
| `frontend/src/lib/onboardingBridge.ts` | `BackendProbe` 加 `seeding` / `seedExists`，一律 `=== true` 解析 —— 旧后端缺字段时自然退回「按 ok 二分」的老行为 |
| `frontend/src/pages/OnboardingWizard.tsx` | 文案映射从深嵌套三元改为 `STEP3_PHASE_TEXT: Record<ModelPhase, string>` 映射表 |
| `backend/tests/conftest.py` | 测试隔离：`TINGKEBANLV_HOME`（临时目录）+ `TINGKEBANLV_SKIP_BACKGROUND_SEED=1` —— 否则走 TestClient 的每个用例都会往用户真实目录里拷 141MB |
| `backend/tests/test_model_seed_background.py`（新） | 11 条：状态机（成功/失败枚举/异常吞/成功后幂等/运行中幂等/失败后重试）+ `seed_exists` 四种情形 |
| `backend/tests/test_onboarding_model_status.py`（重写） | 8 条：字段集合固定、`seeding` 随状态变化、**不可用时必须触发播种**、失败细节不泄漏（只给枚举） |

### 12.4 把 §11.4 的「测试盲区」堵上（新增 4 条断言）

原「首启播种落盘」断言读的是数据目录，而脚本在此之前跑的后端 `--selftest` 已经
替产品播种过一份 —— 所以它无论产品是否播种都会绿。改法是把断言拆成「先破坏、再观察」：

| 断言 | 证明什么 | 为什么原来证明不了 |
|---|---|---|
| 后端自检播种落盘（--selftest 触发，非应用行为） | 只记录事实，**已降为非关键** | 名字里写清它不是产品行为的证据 |
| 清空模型工作副本（为验证「应用自己播种」） | 创造前提：工作副本与完整性标记一起移走 | 原来是「已有 → 断言有」，恒真 |
| **应用启动后自行播种模型（lifespan 后台线程）** | 此后唯一能写回模型的只有后端 lifespan | 日志直证：`开始播种内置模型（base，141.0MB，原因: seeded）` |
| **播种幂等：二次启动不重复拷贝模型** | 重启轮日志**不得**再出现播种行 | 否则每次启动白拷 142MB，还会与识别抢文件 |

### 12.5 文案口径的决定（用户拍板：统一）

| 位置 | 修复前 | 修复后 |
|---|---|---|
| 控制面板（`OverlayControlPanel.tsx`） | `术语提示词自动防循环降级` | **`参与识别的术语自动防循环降级`** |
| 向导第 6 步（`onboarding.ts`） | `参与识别的术语自动防循环`（未变） | 同左 |

判断依据是**受众**而不是「哪个更准确」：「提示词」是 Whisper `initial_prompt` 的实现细节，
面向学生用户的面板不该出现；而两处叫法不一致会让人以为是两个功能。

守卫 `frontend/tests/panel-copy.test.mts`（6 条）钉住这条口径：

- 三个文件的可见文案均不得出现 `提示词` / `initial_prompt`
- 面板与向导的开关名必须包含同一核心短语 `参与识别的术语自动防循环`
- 旧名 `术语提示词…` 不得复活
- **先剥块注释再扫**（这两个文件的注释里大量出现「提示词」，是必要的工程说明）；
  末尾附**变异验证**：往可见文案塞禁词必须报、塞进注释里必须不报

> 教训：一条口径要在「代码 + 测试 + 文案 + 注释」四处同时落地。本轮就是因为先改了
> 面板的代码与注释、却没同步向导口径，才在 §11.5 里留了个待决策项。

### 12.6 第 3 步播种态怎么验（新增 `step3` 模式）

难处：**本机把 141MB 种子拷进数据目录只要 0.1~0.4s**（NVMe + 页缓存），所以
「正在复制模型种子，请稍候」存在但几乎不可见 —— 直接跑一遍只能看到第 3 步一闪而过，
证明不了那句话真的会渲染。

做法：用 CDP 的 **Fetch 域**把 `/api/asr/model-status` 的响应换成
`{ok:false, seed_exists:true, seeding:true}`，把界面**钉在**播种态读真实 DOM；再解除
拦截，验证它自己走到第 4 步。这不是编造数据 —— 被替换的响应正是后端**播种期间的
返回值形状**（字段契约由 `test_onboarding_model_status.py` 钉住，而「后端在播种时确实
会给出这个状态」由 §12.4 的断言覆盖；两段合起来才是完整链路）。

实测（`step3` 模式 3/3）：

```
ok ⑥ 第 3 步显示「正在复制模型种子，请稍候」
   — 第 3 / 6 步 正在准备语音模型 … 正在复制模型种子，请稍候 无需联网下载 …
ok ⑥ 播种期间不停在失败态 — 当前步=3
ok ⑥ 模型就绪后自动跳到第 4 步（无需用户点击） — 当前步=4
```

### 12.7 兜底：播种**始终不完成**时不能让用户卡死（`step3fail` 模式）

上面那条验的是「播种会成功」。但更难的是**万一不会成功**：种子损坏、磁盘满、杀软锁文件、
超慢网络盘……用户不能停在一个永远转圈的界面上。对应前端设计是
`SEED_TIMEOUT_ATTEMPTS = 90`（≈90s）后落 `failed`，给「重试 / 导出日志 / 先跳过，稍后再说」。

做法与 §12.6 同源，只是**把响应一直钉在 `seeding:true`**（永远不完成），等前端自己的
超时兜底触发。实测（5/5）：

```
ok ⑥b 播种超时后进入失败分支
   — 第 3 / 6 步 正在准备语音模型 模型准备失败。 请尝试： 关闭应用后重新打开（会自动重试）
     若反复失败，点击下方按钮导出日志，反馈给开发者 重试 导出日志 先跳过，稍后再说 跳过 上一步 下一步
ok ⑥b 失败分支保留「重试」与「先跳过，稍后再说」 — 重试 / 导出日志 / 先跳过，稍后再说 / 跳过 / 上一步 / 下一步
ok ⑥b 点「重试」后重新进入播种态（不是停在失败）
ok ⑥b 重试后模型就绪仍能自动跳到第 4 步 — 当前步=4
```

> **「点重试后重新进入播种态」这条是缺陷 B 的回归护栏。** 原缺陷最刺眼的症状就是
> 「反复点重试也没用」——因为当时的重试只重新探测、而没有任何人会去播种。
> 现在重试会重走 `seeding` 分支（`onRetry` 清零 `attemptsRef`，后端若仍未就绪则
> model-status 兼作触发点再拉一次播种），所以这条断言必须常驻。

补一句关于「关闭应用后重新打开（会自动重试）」这句恢复说明：**它现在才是真的** ——
重启会重走 lifespan 播种；修复前它是无效引导（§11.4 根因链第 5 条），但文案本身是对的，
所以刻意保留、没有改。这条也解释了为什么 §12.1 选方案 A：只需把承诺补上，不必动文案。

### 12.8 顺带修掉的验收工具缺陷（都在本轮暴露）

1. **`smoke-overlay.cjs` 选靶顺序相关**（真红，11/12 → 12/12）：
   `pages = all` 之后 `pages` 换成了**重新拉取的一批新对象**，而 `overlay` 还是旧对象，
   于是 `p !== overlay` 恒为真、`find()` 可能又把悬浮窗认成主窗口，假报「两个入口串了」。
   历史上它只是**恰好**因为 `/json/list` 把主窗口排在前面才通过。改为按 **target id** 判同一目标。
   教训：拿对象身份去判「是不是同一个目标」，在重新拉取之后必然失效。
2. **`verify_install.py` 播种断言盲区**：见 §12.4。
3. **`drive-onboarding.cjs` 新增 `step3` 模式**：见 §12.6。

### 12.9 遗留与注意

- 「正在复制模型种子」在**本机**几乎不可见（0.1~0.4s）；只有慢盘/冷缓存/杀软扫描的
  用户机上才会停留几秒。文案本身已由 `step3` 模式钉住，不需要真机慢盘复现。
- 播种超时上限 `SEED_TIMEOUT_ATTEMPTS = 90`（≈90s）：超过就落到 `failed` 分支给
  「重试 / 跳过」，兜底「播种卡死」这类没法自愈的情况。**这个值是拍的，尚未有真实
  慢盘数据支撑**，等用户反馈再调。
- `electron:build` **不重建后端**（§11.4 缺陷 A 的配套提醒仍然有效）：只要动了
  `backend/`，发布前必须先用 venv PyInstaller 单独重建 `packaging/out/backend-server`。
- P3 唯一缺口不变：**中文真实网课音频 ≥10min + 逐字稿**仍未拿到。
